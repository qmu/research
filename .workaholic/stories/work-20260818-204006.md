## 1. Overview

Two leftovers from the closed staging-preview mission, both a machine-readable
statement disagreeing with what the repository does: `make help` could not show
`a11y`, and the deployment record still called the merge the deployment.

**Highlights:**

1. `make help`, the `## `-annotated set and `.PHONY` are now identical at 14 names.
2. The record separates commit-on-`main` from site-serving-it, and requires both.
3. One real deploy is quoted in it by run, job and timestamp.

## 2. Motivation

`make help`'s filter was `^[a-zA-Z_-]+:`, which matches no digit, so `a11y` never
reached the formatter — the one documented target a developer could not discover
from the help output was the accessibility check CI runs on every commit. The
deployment record had a different shape of the same fault: its confirmation step
was `git ls-remote origin main`, a probe of GitHub rather than of a running site,
so it would report a successful deployment for a merge whose Worker deploy failed.
The CI/CD policy names that exact state — a green indicator with no evidence of
what was verified — as the thing to prevent.

## 3. Changes

### 3-1. List digit-bearing targets in make help ([590efff](https://github.com/qmu/research/commit/590efff))

Widened the help recipe's character class to include digits. Verified by set
comparison rather than by eye: what `make help` prints, what carries a `## `
comment, and what `.PHONY` declares are now the same 14 names.

### 3-2. Confirm the deploy, not just the merge ([ba8ae95](https://github.com/qmu/research/commit/ba8ae95))

Rewrote `.workaholic/deployments/research-site.md` so the procedure states both
post-conditions of a merge and the confirmation requires three checks — readiness,
the commit on `main`, and the deploy job for that commit succeeding plus the site
responding. The staging Worker was judged a step of the existing target, not a
second record: it has no trigger, artifact or release decision of its own.

## 4. Outcome

The two artifacts a developer reads to find a command and to prove a release now
match the workflow that runs. A follow-up commit ([1ebad62](https://github.com/qmu/research/commit/1ebad62))
removed a `/robots.txt` assertion from the new confirmation step — Cloudflare
serves its own Managed robots.txt ahead of the origin file, so a healthy deploy
would have failed it.

## 5. Concerns

### The routine cannot run the confirmation it just wrote

- **Severity:** moderate
- **Description:** the `[Implement]` container's network policy denies the endpoint (`curl: (56) CONNECT tunnel failed, response 403`), so check 3's HTTP half is unrunnable by the runner that ships most often (see [ba8ae95](https://github.com/qmu/research/commit/ba8ae95) in `.workaholic/deployments/research-site.md`)
- **How to Fix:** allow `staging-research.qmu.co.jp` in the environment's network policy, or keep it a developer-session step and keep the record's instruction to report it unrun

### No probe can prove which commit the staging site serves

- **Severity:** moderate
- **Description:** the built site carries no build stamp, so an HTTP 200 is compatible with a failed deploy that left the previous build live; check 3 compensates with an Actions-API read (see [ba8ae95](https://github.com/qmu/research/commit/ba8ae95) in `.workaholic/deployments/research-site.md`)
- **How to Fix:** emit a `/version.json` carrying the commit sha from the VitePress build and assert check 3 on it, collapsing both halves into one probe

## 6. Successful Development Patterns

- Reading the open deferred-concern set *before* writing a confirmation step
  caught a false assertion that had already been measured live — the concern
  stream is a source of production facts, not only a backlog.
- Proving a help-text fix by diffing three derived sets beat re-reading the
  output: it states the property, not the instance.
