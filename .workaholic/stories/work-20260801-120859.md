## 1. Overview

The `token-metering` article opened by describing the topic as measuring "whether the **input** tokens an LLM API bills for can be counted without the provider's tokenizer library" — which reads as though the *topic* is input-only. It is not. Two different capabilities were being conflated:

- **Pre-flight prediction** — count input *before* the call, without the provider's tokenizer. Input-only **by necessity**: output tokens do not exist yet.
- **Post-hoc actual usage** — read consumed input **and** output back off the response's `usage` field, after the call.

This branch adds the second as an explicit axis inside the topic (Option A, per the owner's scope decision) and rewrites the framing so the two are never conflated again.

**Highlights:**

1. `domain/usage-survey.ts` — the axis as pure data + a pure renderer, with per-row provenance.
2. Subjects span all three surface kinds the ticket required: direct provider APIs, an **agent-SDK layer**, and the **domain-specific** case (Perplexity, which bills search separately from tokens).
3. Dimensions include the subtle streaming case with its **exact opt-in string**, and what the reachable SDK layer does to the figures.
4. The introduction now names both capabilities and states how they reinforce each other.
5. **No fabrication, machine-checked** — a test asserts a keyless row may not claim `reported` for any dimension.

## 2. Motivation

The known starting evidence was that the LLM comparison instrument already reads `outputTokens` from every integrated provider, so at least output usage is demonstrably available across the direct APIs. The survey turns that incidental knowledge into an explicit, per-subject, evidence-based result — and covers the two places it is genuinely uncertain: streamed responses, and wrapper layers.

## 4. Outcome

Each row records: consumed input and output on a non-streaming response; the streaming case (`reported` / `opt-in-required` / `not-reported` / `unknown`) with the exact opt-in flag; the SDK layer's handling (`preserved` / `aggregated` / `dropped`); the extra fields named as the response names them (cached input, reasoning tokens, search units); and its own provenance.

The rendered table carries a note stating plainly that **no subject has been surveyed against a real response yet** — so a reader is never left inferring that an `unknown` means "not supported".

## 6. Concerns

- **`make drift` is blind to this change.** Any renderer edit for a frame-composed topic passes drift without being exercised. "Drift is green" must not be read as "the new section works" — unit tests are the only real gate here. This applies to every topic with a measured frame, not just this one.
- **The published page will not show the survey until a real run.** Reviewers looking at `docs/research-reports/token-metering-comparison.md` in this PR will not find the new section. That is expected; see section 5.
- **Every cell is `unknown` today, by design.** The rows declare what will be measured. The risk is that a later session "helpfully" fills them in from provider documentation — which is exactly what the anti-fabrication test exists to prevent, and why that test asserts the *absence* of claims rather than their presence.
- **The agent-SDK subject is generic.** It names the surface kind rather than a specific SDK, because which wrapper to survey is part of the proposal the owner approves. The real survey pins it.

## 7. Successful Development Patterns

- **Assert the absence of claims.** The load-bearing property of a keyless research scaffold is that it asserts nothing unobserved. Testing that every row is `fixtured` with every dimension `unknown` and no extra fields catches the one failure mode that would quietly turn a placeholder into a published falsehood.
- **Fix the framing, not the measurement.** The domain always modelled input counting honestly; what said "input only" was one sentence in the introduction. The reader took it as the topic's scope rather than the method's limit.
- **Model the opt-in as a first-class cell.** Streaming is where a meter fails silently — several providers omit `usage` from a streamed response unless the request asks for it, so a meter tested against non-streaming responses records zero the moment it switches. The exact flag string belongs in the table, not a footnote.
- **Verify the renderer directly when the page cannot show it.** Rather than concluding "drift is green, so it works", the survey render was exercised on its own and asserted in tests.
