## 1. Overview

`scripts/publish-research.sh` skipped destinations it could not prove it wrote,
and told the operator how to keep the downstream text. That instruction was
inverted: following it guaranteed the file's destruction on the next run.

This unit gives the publish ledger a third state — an explicit downstream-owned
mark — so "qmu-co-jp owns this file" can be stated in committed data instead of
held in an operator's memory, and corrects every instruction that said otherwise.

Ticket: `20260801223000-publish-guard-remedy-is-inverted.md`.

## 2. Motivation

The ledger recorded exactly one fact per destination — *the hash this exporter
last emitted* — and the guard derived ownership from it. So the skip message's
second remedy,

> record the destination's hash in `scripts/publish-ledger.tsv` to keep the
> downstream text

named the one action that guarantees the opposite. Recording the hash satisfies
the **copy** branch's precondition (`hash matches the ledger` → "untouched since
our emit"), so the very next `copy --all` overwrites the downstream-authored
prose — silently, because the guard now believes the exporter owns the file.

There was no way to express the decision at all. The only state that preserved
downstream text was **no ledger entry**, which the guard re-reported as a loud
skip on every run: permanent protection and a permanent warning were the same
state.

This was encountered live on 2026-08-01 while shipping PRs #68–#76. The guard
correctly skipped `image-generation.md` (downstream carries the measured
2026-07-17 trial article; this repo's source is a keyless `trials: 0`
regeneration) and `agent-vm-comparison.md` (downstream carries hand-edited
prose, `provenance: authored-fixture-translation`). The developer ruled "keep the
downstream text". Following the script's own instruction would have destroyed
both.

## 3. Changes

The hash column now carries two different **kinds** of fact, and the distinction
is the fix:

| value | kind | meaning |
| ----- | ---- | ------- |
| a sha256 | observation | this is the text we last emitted |
| `downstream` | decision | qmu-co-jp owns this file; never write it |

- **The decision is read first**, short-circuiting the hash comparison. A marked
  destination is never classified as a divergence, and its content is irrelevant
  — the mark holds whether the file matches the source, differs, or is absent.
- **Reported as an exclusion, not a warning**: `downstream-owned (excluded)` on
  stdout, counted separately from skips, so a clean publish run no longer emits a
  misleading "authored downstream" line on stderr.
- **`--force` no longer reaches a marked destination.**
  `--force-downstream-owned` is its own deliberate opt-out, and it **keeps** the
  mark — one override is not a revocation.
- **`mark-downstream <dest-path>…`** sets the mark, so the corrected instruction
  is executable rather than a hand-edit of a TSV. The instruction that got
  followed wrongly was exactly that shape.
- **The header and skip message now describe what the code does**, and say
  explicitly why recording the hash is the wrong remedy.
- `image-generation.md` and `agent-vm-comparison.md` are marked.

## 5. Historical Analysis

The ownership guard itself (PR #71) was correct and is untouched: it did stop the
overwrite it was built to stop. What was missing was the *other* half of the
rule. The guard could enforce "the exporter owns this" but had no vocabulary for
"qmu-co-jp owns this", so it expressed the second case as an unresolved instance
of the first — and the remedy text papered over the gap with an instruction that
inverted it. The rule stated in `docs/adr/0003-*` and in the script header stands
unchanged; only its enforcement and its instructions needed repair.

## 6. Concerns

- **No `unmark-downstream`.** Reclaiming a destination for the exporter means
  editing the ledger row by hand. Deliberate — revoking a standing decision
  should not be one flag away — but worth a command if it recurs.
- **`../qmu-co-jp` carries unresolved divergences.**
  `llm-accuracy-comparison.md` and `llm-speed-comparison.md` have uncommitted
  modifications from the 2026-08-01 ship session. Untouched by this work
  (dry-run only), but they need a disposition; this ticket's mechanism is now the
  correct way to record it if downstream should win.

## 7. Successful Development Patterns

- **The acceptance test had to span two runs.** The second run is what destroyed
  the text, so a single-run check would have passed throughout the defect's
  entire life. When a bug is "the state left behind is wrong", the test must
  execute the operation twice.
- **Mutation-test with the defect's own shape.** Breaking the new branch proves
  the assertions are wired; reintroducing `ledger_record` on the exclusion path —
  the original failure exactly — is what proved assertion 9 is load-bearing
  rather than decorative. Four mutations were run, each verified to have actually
  applied before its result was read.
- **A mutation harness that restores with `git checkout --` destroys uncommitted
  work under test.** It silently reverted the implementation mid-run here.
  Commit before mutation-testing.
- **Comment lines in a machine-sorted file need sort keys.** The ledger's own
  header had shuffled into nonsense because the writer re-sorts the whole file
  with `LC_ALL=C sort` and comments sort as data. Zero-padded numbers fix it;
  plain `1..11` does not, because byte order puts `10` before `2`.
