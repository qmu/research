## 1. Overview

`make install` on a clean checkout left three modified lockfiles behind — 75
lines that moved no dependency version, only the `libc` arrays npm 11 writes and
the pinned Node 22's npm 10 strips out again. The repository now declares the
toolchain its lockfiles were written by, and checks it.

**Highlights:**

1. `make install` is a no-op: `git status` is empty afterwards.
2. Each `package.json` declares `engines` for Node and npm; all three lockfiles
   were regenerated under it.
3. `make lockfiles` runs the install and fails by name if anything was rewritten.

## 2. Motivation

The churn was small, reversible and constant, which is why it survived: every
session paid one `git checkout --` and none of them was the session that fixed
it — and a session that did not notice committed three unrelated lockfiles into
its pull request. Nothing in CI would have caught either. The CI/CD policy asks
that the same inspection command reach the same result whoever runs it; a command
that mutates tracked files on a clean tree does not.

## 3. Changes

### 3-1. Make npm install a no-op on a clean checkout ([4c6d09b](https://github.com/qmu/research/commit/4c6d09b))

Declared `engines` (`node >=22 <23`, `npm >=10.9 <11`) in all three package.json
files and regenerated each lockfile under exactly that — one atomic change,
because `engines` is recorded into the lockfile's own root entry. Added
`scripts/check-lockfile-stability.sh` behind `make lockfiles`, run in CI right
after Install.

## 4. Outcome

The pin was chosen over bumping npm to 11: taking npm 11 into effect needs
corepack or a global install, both system-wide changes this repository does not
authorize. A contributor on npm 11 now gets an `EBADENGINE` warning and a named
CI failure instead of seventy-five silent lines. CLAUDE.md documents both
([6ebae98](https://github.com/qmu/research/commit/6ebae98)).

## 5. Concerns

### The declared npm was inferred from the lockfile format, not read from a CI log

- **Severity:** low
- **Description:** the ticket asked that CI's resolved npm be read from a log, but npm prints no version banner and no step asked for one, so the pin rests on this container's `npm -v` plus the `libc` fields dating the committed files to npm 11 (see [4c6d09b](https://github.com/qmu/research/commit/4c6d09b) in `scripts/check-lockfile-stability.sh`)
- **How to Fix:** nothing further — `make lockfiles` now echoes `node -v` / `npm -v` as its first line, so the next reader has the answer in every CI log; confirm it there once and the inference is retired

## 6. Successful Development Patterns

- The guard was proven in both directions before landing: green on the fixed
  tree, and red — naming the file — with one lockfile restored from `origin/main`.
  A check only tested on the passing case is a check with an unknown failure mode.
- Hashing the manifests either side of the install, rather than reading
  `git diff`, kept the guard honest on the very branch that edits those files.
