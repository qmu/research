## 1. Overview

The docs staging deploy was implemented but unverified — PR #117 shipped with a
handoff because an unattended run holds no Cloudflare credentials. The developer
supplied the two secrets, the deploy ran for real, and the mission closes with
the evidence rather than with a ticked box.

**Highlights:**

1. `staging-research.qmu.co.jp` serves the site: 367 assets, custom domain bound
2. Mission closed `achieved` — all three acceptance criteria now verified live
3. One divergence found: the served `robots.txt` is Cloudflare's, not this repository's

## 2. Motivation

The mission's three acceptance items were already ticked when #117 was written,
but the run that ticked them could not contact Cloudflare — the deploy job had
never executed. A mission left open on that basis rots into a false negative;
closed on that basis it becomes a false positive. Both were avoidable once the
credentials existed.

## 3. Changes

### 3-1. Close the docs staging deploy mission as achieved ([b7f54c0](https://github.com/qmu/research/commit/b7f54c0))

Records the deploy evidence as a mission changelog line and moves the mission to
`archive/` via `close.sh`, and files the `robots.txt` divergence found during
verification as a concern.

## 4. Outcome

Every merge to `main` now publishes the built VitePress site with no manual step.
Verified live: `/` and `/research-reports/` return 200 `text/html`, an unknown
path returns the built 404, `/sitemap.xml` is absent, and both pages carry
`<meta name="robots" content="noindex, nofollow">`.

## 5. Concerns

### The deployed robots.txt is Cloudflare-managed, not the one this repository ships

- **Severity:** moderate
- **Description:** Cloudflare's zone-level Managed robots.txt is served ahead of the built file, so `/robots.txt` carries `User-agent: * / Allow: /` before this repository's `Disallow: /`; merged per the robots rules, the blanket disallow configured in `docs/.vitepress/config.ts` is not the rule a crawler applies (see [b7f54c0](https://github.com/qmu/research/commit/b7f54c0) in `.workaholic/feedbacks/20260819044612-the-deployed-robots-txt-is-cloudflare-managed-not-the-one-this-repository-ships.md`)
- **How to Fix:** Pick the owning layer — drop the repo-side `Disallow: /` and document `noindex` as the mechanism, or disable Managed robots.txt on the `qmu.co.jp` zone; use Cloudflare Access if staging must actually be uncrawlable

## 6. Successful Development Patterns

- A declared `verification_handoff:` is worth more than a retry: the branch merged on its own evidence, and the one thing it could not prove was proved in a separate step once the credential existed — the divergence found there (`robots.txt`) would have been invisible to any amount of local testing.
