## 1. Overview

This branch fixes the repository's only general-purpose gate. Every per-package `make` target discarded the exit status of every package **but the last**, so `make test` returned **0** on a tree that failed its own tests — and `ci.yml` invokes these same targets.

The mechanism is small and total: `@for p in $(PACKAGES); do (cd $$p && npm test); done` is **one** recipe line, so make evaluates one exit status — the shell's — and a POSIX `for` loop's status is its **last iteration's**. Because `packages/tech` (essentially all of this repo's code) is listed **first**, it sat permanently in the masked position.

**This is not theoretical.** `main` was genuinely red at `0b09ddc` while CI reported green, and this branch reproduces that incident and its fix, measured.

**Highlights:**

1. All five per-package targets (`install`, `build`, `test`, `lint`, `format`) now share one status-accumulating `for_each_package` shape that runs every package, returns non-zero if any failed, and prints `make: <step> FAILED in: <packages>` naming each one.
2. Added `scripts/check-make-gate.sh` (`make gate`) — the regression test the ticket calls "the point of this ticket" — asserting **raw** exit codes with the failure in **first, middle and last** position, plus healthy-tree controls.
3. Wired `make gate` into `ci.yml` as its **first** step, so a masking regression fails before the gates that would be masked by it.
4. **Proven against real history**, not just a synthetic fixture: at `0b09ddc` the original Makefile returns **0** and this branch's returns **2**, naming `packages/tech`.
5. `CLAUDE.md`'s "Never verify through `make`" guidance was updated — it described the defect as "filed and unfixed" and instructed every developer and agent to route around the repository's own runner.

## 2. Motivation

`CLAUDE.md` codifies "One runner. All common operations run through `make`; CI invokes the same targets." The Makefile therefore *is* the contract — which is exactly why a lying Makefile is a severity-1 defect rather than a cosmetic one: every developer and agent is instructed to trust it.

`workaholic:operation` / `policies/ci-cd.md` names this failure outright — the state to prevent is "treating a green indicator, absent any evidence of what the inspection actually verified, as proof the code is healthy". The single inspection command was manufacturing precisely that indicator, which is worse than having no command at all.

## 4. Outcome

- `install`, `build`, `test`, `lint`, `format` each return non-zero when **any** package fails, in **any** position, and name every failing package.
- `make gate` proves that property against a scratch fixture in about a second, and runs first in CI.
- `build`'s and `install`'s separate `docs` lines are untouched — they were already checked, and folding them into the loop would have re-created the bug.
- A new `DOCS_DIR` variable exists **solely** so the gate can point the docs line at a no-op fixture. Nothing else should override it.

## 5. Historical Analysis

The ticket's blast-radius analysis held up under re-measurement. At `0b09ddc`, with genuine installs in both packages:

| what | raw exit |
| --- | --- |
| `cd packages/tech && npm test` (ground truth) | **1** — `AssertionError: expected undefined to be true`, the failure the ticket named |
| `cd packages/industry && npm test` (ground truth) | **0** |
| `make test`, **original** Makefile | **0** ← the incident |
| `make test`, **this branch's** Makefile | **2**, printing `make: test FAILED in: packages/tech` |

A first attempt at this probe symlinked the current tree's `node_modules` into the old checkout. Both packages then failed with `TS2688: Cannot find type definition file for 'node'` — which made the *last* package fail, which made even the **original** Makefile return non-zero, i.e. a **false pass** of the acceptance test. That is exactly the trap the ticket's Quality Gate warned about ("an uninstalled package fails for the wrong reason and will fake a pass"). The probe was redone with real `npm install` in both packages.

## 6. Concerns

- **This gate will now correctly go red where it previously went green.** That is the intent. Any branch carrying a genuine `packages/tech` failure will start failing `ci`. `main` itself is green (`cd packages/tech && npm test` → exit 0), so this is not an active breakage.
- **`build-research-tech.yml` is deliberately kept**, with the reason recorded in its own header. It duplicates checks that `ci.yml` runs through `make`, which reads against "One runner" — but its `paths:` filter means it does **not** run for a change that breaks `packages/tech` without touching `packages/tech/**`, which is the `0b09ddc` shape exactly. Removing it is a separate change, and only after a reviewer has seen the fixed `ci.yml` go red on its own.
- **`packages/industry` has zero test files** and runs with `--passWithNoTests`, so its green remains weak evidence on its own. Out of scope here, but it means the honest gate is still carried almost entirely by `packages/tech`.
- **A minted ticket rides along in this PR**: `20260801121500-claim-subject-exceeds-commit-length-limit.md`, for a blocker hit elsewhere in the same drive (see section 9). It is unrelated to the Makefile change and needs no review beyond "should this be queued".

## 7. Successful Development Patterns

- **Mutation-test the guard, never just observe it green.** Reinstating the old bare-loop recipe makes the gate fail **9** assertions — the FIRST- and MIDDLE-position cases across `test`/`build`/`lint` plus the three "names the failing package" checks — while the LAST-position cases still pass. That asymmetry *is* the defect's mechanism, reproduced on demand, and it is what proves the gate is not vacuous.
- **Assert ordering-independence explicitly.** Testing only the first position would be satisfied by reordering `PACKAGES` — a "fix" that hides the bug behind luck and re-exposes whichever package is added next.
- **Test the recipe shape, not the real suites.** The bug lived in the recipe, so a fixture of three trivial `package.json`s proves it in a second and makes position independently assertable.
- **A failed verification probe is a finding, not noise.** The contaminated first probe would have "passed" the acceptance test for the wrong reason; noticing *why* it passed is what made the real measurement trustworthy.
