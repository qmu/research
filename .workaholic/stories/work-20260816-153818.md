## 1. Overview

The `foundation-models` topic is a reference catalog, not a measurement, but its
pages carried the seven-section verification outline because its renderer composed
through the standard-article renderer every measured topic shares. It now renders
on its own four-section outline in both languages.

**Highlights:**

1. Overview / Coverage / Catalog / Sources (概要 / 収録範囲 / カタログ / 出典), selected per topic from the registry's existing `kind` marker.
2. Both outlines stay validated repo-wide and keep EN→JP heading pairs, so the exception is governed rather than an opt-out.
3. The trend block no longer attaches to a topic that can never gain a trend.

## 2. Motivation

The uniform outline was deliberate: `article-outline.ts` exists so every topic
reads as the same article in different languages. That premise holds for a
measurement and breaks for a catalog, which has no research purpose, no
measurement targets and no reproduction cost — yet the page opened on "1. Research
Purpose" and buried its content in "7. Verification Data". The reporter compared
it against the topic's own archived frames, which used a compact `Catalog` /
`Sources` shape before the standardization.

The ticket left one fork open: govern the exception, or let the catalog topic opt
out of validation and render freely. Opting out would also drop it from the EN→JP
heading-pair map that keeps Japanese headings stable, so the page would fork from
its English source with nothing checking it. Resolved as a second validated outline.

## 3. Changes

### 3-1. Give the foundation model catalog page its own non-verification outline ([2d81317](https://github.com/qmu/research/commit/2d81317))

Added `CATALOG_OUTLINE` beside `ARTICLE_OUTLINE`, both reached through
`ARTICLE_OUTLINES`, with `articleOutlineProblems` taking the outline kind as a
third argument defaulting to `"standard"` — so all twenty-odd existing call sites
read unchanged and an omitted argument is checked strictly rather than skipped.
Selection is keyed on `TopicSpec.kind`, so the catalog renderer, the translation
prompt's heading pairs and the conformance sweep all read one selector.

## 4. Outcome

Both catalog pages carry the new sections and neither contains a `Research
Purpose` / `調査の目的` heading; the other 15 English and 14 Japanese articles keep
the unchanged seven. The English page regenerates byte-identically and the
VitePress build renders both. Nothing under `docs/research-reports/history/`
changed, per the reporter's explicit exclusion.

## 5. Concerns

### The Japanese catalog page is hand-authored, not pipeline-generated

- **Severity:** moderate
- **Description:** `foundation-models.insights.ja.md` was written by hand, not regenerated: the outline change invalidated the committed page and `research:translate-report` needs `ANTHROPIC_API_KEY` (see [2d81317](https://github.com/qmu/research/commit/2d81317) in `docs/research-reports/foundation-models.insights.ja.md`). Its figures are copied from the English page and its frontmatter says what it is, but it is not reproducible by running a command, which every other Japanese page is.
- **How to Fix:** Run `npm run research:translate-report -- foundation-models` with a live key and diff against the hand-authored page; ticket `20260816155216-regenerate-the-japanese-catalog-page-through-the-live-translation-path` carries the steps and a `verification_handoff`.

### A keyless research:translate-report overwrites a published page with a stub

- **Severity:** moderate
- **Description:** `translationClient()` falls back to `createFixtureTranslationClient` when `ANTHROPIC_API_KEY` is absent and the runner writes that straight over the published Japanese page, so the documented command replaces a real page with one placeholder line (see [2d81317](https://github.com/qmu/research/commit/2d81317) in `packages/tech/src/research/report-translation-runner.ts`). The keyless `--fixture` path is safe by contrast.
- **How to Fix:** Make the runner refuse when no key is present rather than substituting the stub client, so a keyless invocation is a no-op instead of a destructive one.

## 6. Successful Development Patterns

- Keying new behavior on an existing per-topic marker (`TopicSpec.kind`) rather than a new list of topic ids — the marker was already read in three places for the same kind of decision, and a new list would be a second registry to keep in sync.
- Defaulting the new `articleOutlineProblems` argument to the strict outline — a forgotten argument fails loudly instead of silently skipping validation, which is what made the untouched call sites safe to leave alone.
