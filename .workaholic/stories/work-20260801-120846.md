## 1. Overview

The dispersion gate that stopped the generational section labelling noise as a direction landed earlier (`32d5165`). This branch closes what that change deliberately left open: the reader still could not see the **sample** a direction rested on, and two sampling questions were unanswered.

All three remaining criteria are met — and the trial-depth answer rests on something the ticket had not anticipated.

**Highlights:**

1. The delta table gains a **Trials** column, drawn from each metric's own contributing-trial count. Per metric, not per run — the structural probes execute once while the speed probe repeats, so one caption would have been wrong for half the rows.
2. **Do not raise `--trials`** — not because 3 is enough, but because **more trials cannot move this gate at all** (section 5).
3. **Verdicts stay per effort level**, because `low`/`medium`/`high` are different operating points rather than repeated samples.
4. Both decisions recorded in `docs/adr/0008-generational-verdict-sampling.md`.
5. A minted ticket for the real lever the analysis exposed.

## 2. Motivation

A mechanically-derived verdict is still a claim, and `workaholic:implementation` / `objective-documentation` requires verifiable language. "−38%, regressed" is unreadable as a claim without the sample it came from: the same configuration re-swept hours apart moved sustained throughput by up to 88%, so −38% over 3 trials and −38% over 30 are entirely different assertions. The section stated neither.

## 5. Historical Analysis

**Why more trials would not help.** The gate is

```
|mean_new − mean_former|  >  sd_former + sd_new
```

`sd` is the sample standard deviation — an estimate of how much *individual trials* scatter. It does **not** shrink as `n` grows; only its estimate stabilises. So spending on 10 or 30 trials per paired configuration leaves the threshold essentially where it is and converts **none** of today's `indistinguishable` throughput results into supported directions.

That reframes the ticket's second question entirely. The current count of 3 is "sufficient given the gate" — which the acceptance criterion explicitly allowed — but for a sharper reason than "good enough": the gate is a **dispersion** test, while the claim being made is about the two **means**. The statistic that matches the claim is the standard error of the difference, `sqrt(sd_a²/n_a + sd_b²/n_b)`, which *does* shrink with `n`.

**Why per-effort stays.** Aggregating across the ladder would report a figure no configuration was ever measured at, and would bury the finding itself — the noise is concentrated at `high` (±30–88%) while `low` reproduced to ±1%. Per-effort is where the sample is thinnest, which is precisely why the gate is applied there.

## 6. Concerns

- **The project currently has no lever for the suppressed directions.** Raising the sample does nothing under this statistic, and lowering the threshold would restore the original defect. Filed as `20260801124500-generational-gate-uses-dispersion-not-standard-error.md`. It was **not** implemented here because it changes which findings the published article asserts — a research-reporting decision with an owner, not a refactor.
- **`make drift` cannot catch regressions in this section.** It stayed byte-stable across a change that adds a table column, because the fixture sweep carries no registry pairing and so produces no generational section at all. Anything in `generational-delta.ts` must be covered by unit tests; the drift gate is blind to it.
- **The gate's conservatism is invisible from its output.** A future reader seeing five of six directions withheld would reasonably conclude "we need more trials" and would be wrong. ADR 0008 records this, but the rendered section still does not say it.
- **Touches no committed article.** The published pages are not re-rendered here, so the `Trials` column appears only on the next real sweep's report.

## 7. Successful Development Patterns

- **Answer the sampling question by checking the statistic, not by intuition.** "Should we measure more?" looked like a cost/benefit call and was actually a mathematical one with a definite answer. Recording *why* the answer is no is what makes it durable — otherwise the next session re-opens it.
- **Record a decision where the code can be read from.** Both decisions live in an ADR, not only in a ticket that will be archived out of sight.
- **Surface data that already exists before capturing more.** `MetricStat.n` had recorded the per-metric trial count all along — its own comment says "so a reader can tell a 3-trial mean from a 1-trial one" — but it never reached the delta table.
- **File the change you decided not to make.** The standard-error alternative is the actual answer to the project's problem; leaving it as prose in a Final Report would have discarded it.
