# `make install` rewrites all three lockfiles under the pinned Node 22

## Overview

Running the documented `make install` on a clean checkout leaves three modified
files behind:

```
$ git status --short
 M docs/package-lock.json
 M packages/industry/package-lock.json
 M packages/tech/package-lock.json
$ git diff --stat -- '*package-lock.json'
 docs/package-lock.json              |  3 ---
 packages/industry/package-lock.json | 30 --------------------------
 packages/tech/package-lock.json     | 43 +------------------------------------
 3 files changed, 1 insertion(+), 75 deletions(-)
```

The diff is almost entirely the removal of `"libc": ["glibc"]` / `["musl"]`
blocks from optional platform packages, plus one added `"hasInstallScript": true`.
Those are lockfile fields npm 11 writes and npm 10 does not, so the committed
lockfiles were generated by an npm newer than the one the pinned Node ships.

Measured on 2026-08-18 in the `[Implement]` container while running the CI gate
for `20260818131500-deployment-record-still-says-the-merge-is-the-deployment.md`:

| Fact | Value |
| --- | --- |
| `node -v` | `v22.22.2` — matches `.nvmrc` (`22`) and `ci.yml`'s `node-version: "22"` |
| `npm -v` | `10.9.7` |
| `lockfileVersion` in all three files | `3` |

The consequence is not a broken build — `make build`, `test`, `lint`, `a11y`,
`publish-guard` and `drift` were all green afterwards. It is that **every session
that runs the documented install command must notice and revert three unrelated
modified files before committing**, and a session that does not notice commits
lockfile churn into an unrelated pull request. This run reverted them by targeted
`git checkout --`; the next one has to know to do the same.

Which side is wrong is genuinely open: the repository pins Node 22, whose bundled
npm 10 cannot reproduce the committed lockfiles, so either the lockfiles are ahead
of the pin or the pin is behind the lockfiles.

## Key Files

- `.nvmrc` — the pin (`22`), and the only place the Node version is stated for a
  developer's machine.
- `.github/workflows/ci.yml` — `actions/setup-node@v7` with `node-version: "22"`;
  whichever npm that resolves to is what CI's lockfiles would be written by.
- `Makefile` — the `install` target (`for_each_package,install,npm install` plus
  `install-docs`).
- `packages/tech/package-lock.json`, `packages/industry/package-lock.json`,
  `docs/package-lock.json` — the three files that move.

## Implementation Steps

1. Establish which npm wrote the committed lockfiles (the presence of `libc`
   blocks dates them to npm ≥ 11) and which npm CI's `setup-node@v7` + Node 22
   actually resolves — read it from a CI log, not from local inference.
2. Decide the fix, and state the reason in the same change: either pin npm
   explicitly (a `packageManager` field per package, or `engines.npm`, or an
   `npm install -g npm@<v>` step) so every environment writes the same lockfile
   shape, or regenerate all three lockfiles with the npm the pin actually ships
   so `npm install` is a no-op on a clean tree.
3. Apply it to **all three** projects — `packages/tech`, `packages/industry` and
   `docs` — since each is an independent npm project with its own lockfile
   (`docs/adr/`, no workspaces), and a fix applied to one leaves the other two.
4. If a durable check is wanted, note that CI has no step that would have caught
   this: nothing runs `git diff --exit-code` after `make install`.

## Quality Gate

**Acceptance criteria** — the checkable conditions that must hold:

- `make install` on a clean checkout leaves `git status --short` empty.

- `git diff --exit-code -- '*package-lock.json'` after the same run — exit 0.

**Gate** — what must pass before approval:

- CI green (`make gate`, `install`, `build`, `test`, `lint`, `a11y`,
  `publish-guard`, `drift`).

## Considerations

- **Do not "fix" this by committing the churn.** The stripped `libc` fields are
  npm 10 writing an older lockfile shape; committing that would make the next
  developer on npm 11 produce the inverse diff, and the two would trade the same
  75 lines back and forth forever.
- The `mission:` relation is inherited from the provoking ticket per the minting
  rule. That mission is already **closed**
  (`auto-deploy-the-docs-site-to-a-cloudflare-worker-on-merge-to-main`), and this
  ticket does not belong to its definition of done — nothing was appended to its
  `## Acceptance`. Clearing or re-pointing the relation is a developer's call.
- Severity is low and the workaround is one command
  (`git checkout -- '*package-lock.json'`), which is exactly why it can persist:
  every run pays a small tax and none of them is the run that fixes it.
